Three Core Design Patterns

1. Factory Pattern

AI providers and meeting platforms are fully pluggable. Change one environment variable (AI_PROVIDER=openai) to switch AI model — zero code changes.

2. Service Layer

All business logic lives in dedicated services: MeetingService, CalendarService, OutlookCalendarService, ConflictService, AgendaService, SmartSlotService.

3. Provider Registry

A central config file defines all supported integrations. Admin panel reads this registry and toggles providers — no deployment needed.

4. State Machine (Frontend)

Chat UI follows a strict flow: Input → AI Summary → Missing Fields → Platform → Slots → Confirmation. Each step is isolated and testable.

AI Prompt Design — how the AI understands the user

"We have a custom-engineered prompt in PromptBuilder.js. Let me show you how it works."

There are exactly 2 AI calls per meeting scheduling:

Call 1 — Extraction

Reads the user's raw text. Returns a strict JSON object with all meeting fields. Handles date parsing, relative time, ambiguity resolution.

Call 2 — Summary

Given the confirmed meeting data, generates a friendly confirmation paragraph that the user sees after the meeting is created.

Actual Extraction Prompt (simplified view)

# System instruction given to the AI ROLE: You are a precise meeting scheduler AI. Extract all meeting information from the notes below. CONTEXT: Today is [current date]. Current time is [current time]. NOTES: """[user's raw text goes here]""" DATE RULES: - "tomorrow" → next calendar day - "Friday" → next upcoming Friday - "now" / "ASAP" → today at current time - "morning" → set time = null, ask the user - "noon" → 12:00 OUTPUT: Return ONLY valid JSON. No markdown. No explanation. { "meetings": [{ "meeting_title": "string or null", "participants": ["Full Name"], "participant_emails": {"Full Name": null}, "date": "YYYY-MM-DD or null", "time": "HH:MM (24h) or null", "duration": "minutes as number or null" }] } # Key rules enforced in prompt: # - NEVER invent a title — use null if not stated # - NEVER default duration — use null if not stated # - NEVER put duration inside the time field # - NEVER guess vague times like "afternoon" — use null

Why this approach is reliable: The prompt gives the AI strict output rules — no markdown, no explanation, only JSON. This prevents hallucination and makes parsing 100% predictable. We spent significant time on edge cases like "tomorrow morning" (time = null), "next Friday afternoon" (time = null), and "in 30 minutes" (date = today, time = now + 30).

Common Q&A — questions USA clients typically ask

What AI model are you using?

By default we use Groq, which runs Llama 3 — it is extremely fast and has a generous free tier. But we also fully support OpenAI GPT-4o, Anthropic Claude, and Google Gemini.

Switching AI providers requires only changing one environment variable: AI_PROVIDER=openai or AI_PROVIDER=claude. No code change is needed. The client can choose based on their performance requirements, data policy, or existing contracts.

What prompt do you use for AI extraction?

We use a custom-engineered system prompt in PromptBuilder.js. The prompt tells the AI: today's date, current time, and strict rules for parsing relative dates like "tomorrow", "Friday", "ASAP", and "now".

The AI is instructed to return only a strict JSON object — no markdown, no explanation. This prevents hallucination and ensures 100% reliable parsing. We handle edge cases explicitly: for example, "morning" or "afternoon" are treated as null (the system then asks the user for an exact time).

There are exactly 2 AI calls per meeting: one for extraction (returns JSON), one for the confirmation summary paragraph.

How many tokens does one meeting scheduling use?

Approximately 1,200 to 1,400 tokens total per meeting.

With Groq's free tier (500,000 tokens/day), this supports approximately 350 complete meeting schedules per day at zero cost.

Is the user's data secure?
  • We use OAuth 2.0 — no passwords are ever stored
  • OAuth tokens are stored encrypted in MongoDB
  • Sessions expire and token refresh is handled automatically
  • The system can be deployed in a private cloud (AWS, GCP, Azure) — no data leaves the client's infrastructure
  • We never send calendar event content to the AI — only the user's raw scheduling request text
Can we add our own calendar or meeting platform?

Yes — the architecture is specifically designed for this. Adding a new meeting platform (for example, Webex or BlueJeans) requires writing one class that implements four methods: createMeeting, updateMeeting, cancelMeeting, getMeetingDetails.

Then register it in the PlatformFactory and the provider registry. No other code changes are needed anywhere in the system.

Same pattern applies for calendar providers (Apple Calendar, Calendly, etc.) and auth providers (GitHub, LinkedIn, Email/Password).

Can it handle team scheduling — checking everyone's availability?

Currently the system checks the organizer's Google Calendar and Outlook Calendar for conflicts, then sends invites to participants.

Full multi-participant availability checking — where each participant's calendar is checked before suggesting a slot — is on the near-term roadmap. This requires participants to also be connected users, or using calendar free/busy APIs from Google and Microsoft (which both support this).

Can it scale to enterprise volume?
  • The backend is stateless Express — it can be horizontally scaled behind a load balancer
  • MongoDB Atlas provides managed, auto-scaling database clusters
  • Session state is stored in MongoDB (not in-memory), so multiple server instances work correctly
  • Groq's free tier handles 350 meetings/day. For enterprise scale, switching to Claude Haiku costs approximately $1 per 1,000 meetings
Why only 2 AI calls? Other tools use 4–5 calls per action.

We designed the extraction prompt to handle everything in one shot — title, date, time, participants, duration, and date parsing all in a single API call. Most systems break this into multiple calls.

Using 2 calls instead of 4–5 gives us:

  • Lower latency — less waiting time for the user
  • Lower cost — fewer API calls = lower token usage
  • Better reliability — fewer API calls = fewer points of failure

If cost is a concern, the second call (summary generation) can be replaced with a template — reducing to just 1 AI call per meeting at roughly 1,000 tokens total.
