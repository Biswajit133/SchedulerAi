1. Product Overview
What SchedulerAI is and who it's built for

SchedulerAI is an AI-powered conversational meeting scheduler. A user describes a meeting in one plain-English sentence in a chat interface; the system extracts the meeting details, checks calendar availability across connected providers, resolves conflicts, lets the user pick a video platform, and creates the event with invites and a join link automatically — with no manual calendar work.

1.1 Who It's For

SegmentUse Case
Individual professionals / managersSchedule 5+ meetings a week without manual calendar juggling, slot-checking, or copy-pasting video links
Executive assistants / adminsSchedule on behalf of others quickly from natural-language requests, with conflict checks already done
Sales / recruiting teamsBook external calls fast across multiple meeting platforms depending on client preference (Zoom, Teams, Meet)
Consultants / freelancersKeep multiple calendars (Google + Outlook) conflict-checked together when booking client time
⚙️
2. Functionality
What it produces, the conversational Q&A flow, and entry points

2.1 What It Produces

A single chat exchange produces, in this order: (1) a structured meeting object extracted from free text, (2) a calendar event created on the user's primary connected calendar (Google or Outlook), (3) a video-meeting join link on the selected platform (Google Meet, Zoom, or Microsoft Teams), (4) calendar invites auto-sent to all participants, and (5) an AI-written one-paragraph confirmation summary shown in the chat.

2.2 Conversational Validator — Missing-Field Q&A

Before a meeting can be scheduled, the chat asks targeted follow-up questions for any field the AI extraction step couldn't fill. This logic lives in MeetingService.findMissingFields() and is asked one field at a time, in this fixed order:

OrderFieldQuestion Asked
1meeting_title"What is the meeting about?"
2participants"Who should be invited? List their names separated by commas, or type 'just me' to skip."
3email_<name> (per participant)"What is the email address for <name>?" — only asked if the email can't be resolved from contacts or calendar history
4date"Please provide the meeting date."
5time"Please provide the meeting time."
6duration"Please provide the meeting duration (e.g. 30 min, 1 hour)."
💡
A user can answer multiple fields in one reply — e.g. "tomorrow 3pm for 30 min" fills date, time, and duration at once. The frontend extracts whatever it can from each answer before re-checking what's still missing.

2.3 Confirmation & Inline Editing (CONFIRM phase)

Once all required fields are filled, the chat shows a summary (title, date, time, attendees, duration, task, owner) and asks the user to reply "confirm" or describe a change. Inline edits are supported in natural language — e.g. "change time to 5pm", "make it 2 hours", "add John as attendee" — parsed and applied without restarting the flow.

2.4 Platform & Slot Selection

StepBehaviour
Platform selectionIf the user named a platform explicitly ("use Zoom"), it's auto-selected. If exactly one meeting platform is connected, it's auto-selected. Otherwise the user is shown buttons for each connected platform.
Slot selection (date + time given)A smart conflict check runs against the connected calendar(s). If free, the requested slot is shown for direct confirm. If busy, the nearest 3-5 free alternatives are offered.
Slot selection (date only)All free slots for that day are listed for the user to pick from.

2.5 Alternate Entry Points — Sign-In Providers

The chat itself only has one entry point (typed text), but the application is gated behind sign-in, which supports two OAuth providers as alternate "ways in" before a user reaches the chat: Google and Microsoft. Five additional OAuth flows exist for connecting calendars/platforms after sign-in: Zoom, Microsoft Teams, and Outlook Calendar (see Section 7, Auth routes).

2.6 End-to-End User Flow

User opens landing page | +-- Sign in with Google ----+ +-- Sign in with Microsoft -+--> authenticated session | v Dashboard (chat + today's agenda) | v User types: "Schedule a sync with Alice tomorrow at 3pm for 30 min" | v POST /api/meetings/extract -> AI parses text into structured meeting(s) | +-- missing fields? --> conversational Q&A (Section 2.2) --+ | | v | Confirmation summary <--------------------------------------------+ | v Platform selection (if >1 connected) -> Slot selection / conflict check | v Email resolution for any unconfirmed participant | v POST /api/meetings/schedule -> event created + invites sent + join link generated | v Confirmation card: title, time, attendees, join link, calendar link

3. Conversational Architecture
Frontend state machine + shared meeting schema + request protocol

3.1 Orchestration — useChatFlow Phase State Machine

Unlike a linear agent pipeline, the chat is a client-side state machine (frontend/src/hooks/useChatFlow.js) that routes each user message to a handler based on the current phase, then transitions to the next phase. There is no SSE streaming — every step is a discrete REST call.

PhaseMeaning
IDLEAwaiting a new scheduling request, or just finished one
PICKINGUser is choosing which of several extracted meetings to proceed with
MISSINGAsking the field-by-field Q&A from Section 2.2
EMAIL_CONFIRMResolving/confirming a participant's email address
CONFIRMShowing the summary, accepting "confirm" or an inline edit
PLATFORMUser picking a meeting platform from connected options
SLOTSUser picking a time slot from available options
DONEMeeting scheduled; ready for the next request
CANCEL_CONFIRMConfirming a meeting cancellation ("Are you sure?")
RESCHEDULE_TIME / RESCHEDULE_CONFIRMCollecting and confirming a new time for an existing meeting
FOLLOW_UP_SELECTUser picking which past meeting to schedule a follow-up to
NEEDS_NEW_TIMERequested time was in the past; asking for a future time

3.2 Shared Meeting Schema

Every phase reads and writes the same meeting object, defined by the extraction prompt in backend/src/services/PromptBuilder.js:

{
  "id": "unique-id-1",
  "meeting_title": "string | null",      // concise title, never invented
  "participants": ["Full Name 1", ...],
  "participant_emails": { "Full Name 1": "email | null" },
  "task": "string",                       // what needs to be done
  "owner": "string | null",               // person responsible
  "deadline": "YYYY-MM-DD | null",
  "date": "YYYY-MM-DD | null",
  "time": "HH:MM (24h) | null",           // start time only, never a duration phrase
  "duration": "number (minutes) | null"   // never defaulted — always asked if missing
}

3.3 Request/Response Protocol

Plain REST + JSON, not Server-Sent Events. Each chat phase maps to one backend call:

PhaseEndpoint Called
ExtractionPOST /api/meetings/extract
Re-validate after Q&A answersPOST /api/meetings/validate
Slot listing (date only)GET /api/meetings/slots
Smart conflict check (date + time)GET /api/meetings/suggest
Connected platforms listGET /api/integrations
Final schedulingPOST /api/meetings/schedule
Confirmation summary textPOST /api/meetings/summary

4. Services — Technical Detail
backend/src/services/*.js and backend/src/meetingPlatforms/*.js

4.1 PromptBuilder — AI Prompt Construction

RoleBuilds the extraction prompt and the summary prompt sent to the active AI provider
AI calls2 per meeting — 1 extraction, 1 summary
ProviderRouted via ProviderFactory — supports groq (default), openai, claude, gemini, selected by AI_PROVIDER env var
Date handlingAll relative dates ("tomorrow", "next Friday", "asap") are resolved against the server's current date/time before being sent to the model
GuardrailNever invents a title or defaults a duration — both are left null and routed to the Q&A flow if the user didn't state them

4.2 MeetingService — Orchestrator

RoleCoordinates extraction → missing-field detection → availability check → platform creation → invite sending → summary
Key methodsextractMeetingInfo(), findMissingFields(), applyFieldAnswers(), checkCalendarAvailability(), smartSuggestSlots(), createGoogleMeeting(), sendInvites(), generateSummary()

4.3 ConflictService — Slot Availability

RolePure logic, no AI — computes free/busy slots and checks a specific slot for conflicts
Multi-calendargetAvailabilityFromBoth() merges Google + Outlook busy times before computing free slots

4.4 CalendarService & OutlookCalendarService

CalendarServiceGoogle Calendar API wrapper — getEvents(), createEvent() (with optional Google Meet link via conferenceData), updateEvent(), deleteEvent(), searchAttendees(), getRecentMeetings()
OutlookCalendarServiceMicrosoft Graph API mirror of the same methods; extracts Teams join URLs from onlineMeeting.joinUrl when present
Demo fallbackIf the user isn't authenticated with a calendar provider, calendar reads/writes fall back to mock data rather than failing the chat

4.5 Meeting Platform Providers

Common interface defined in MeetingPlatformProvider.js (createMeeting, updateMeeting, cancelMeeting, getMeetingDetails), instantiated by PlatformFactory.create(platform).

ProviderStatusFlow
Google Meet✓ ImplementedDelegates to CalendarService — Google auto-generates the Meet link via conferenceData
Zoom✓ ImplementedCreates a Zoom meeting via the Zoom API, then embeds the join URL in the Google Calendar event description
Microsoft Teams✓ ImplementedTries to create a Teams online meeting via Graph API for a real join URL; on personal-account failure, falls back to Outlook's isOnlineMeeting: true auto-generated link
Webex✗ StubAll methods throw "not yet configured" — registered in the factory but not implemented

4.6 IntegrationService — Provider Registry

RoleReports which calendar/meeting providers a given user has connected, and their default choice, by reading providerRegistry.js against the user's stored tokens
No AI callsPure registry lookup, used to populate the PLATFORM-phase selection buttons

⚠️
Only one AI provider key is required — whichever matches AI_PROVIDER. ProviderFactory.create() throws immediately at startup if AI_PROVIDER is set to an unsupported value, so a typo here fails fast rather than degrading silently.
✅
Optional integration keys (Zoom, and by extension Teams/Outlook/Webex credentials configured elsewhere) degrade gracefully: providerRegistry.js only marks a meeting/calendar provider available if it's been implemented and connected — the chat's platform-selection step simply won't offer an unconnected provider, rather than crashing.

SymptomLikely CauseFix

Chat keeps re-asking for an already-given fieldThe field wasn't recognized in the user's free-text answer (e.g. ambiguous date phrase)Answer with an explicit value, e.g. an exact date or "HH:MM" time instead of a vague phrase like "afternoon"
